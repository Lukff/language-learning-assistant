# Language Learning Assistant — Technology Decisions

> Project context document. Source of truth for current technology choices.
> Can be updated at any time without changing the project instructions.
> Last updated: 19/07/2026

## Desktop application

- **Framework:** Wails **v3** (alpha) + Go.
  - **Pinned version** in `go.mod`; upgrading from alpha is a deliberate task, never in the middle of a feature. Migrate to beta/stable when it's released.
  - **Rationale for the switch (was Tauri/Rust):** the dev's prior experience with Go/Wails outweighs Tauri's marginal advantages for a solo project; v3 was chosen over v2 because the API changes substantially between them and starting on v2 would mean a certain rewrite, while the app uses little of the framework's surface (single window, dialogs, drag-and-drop, bindings, events).
  - **Thin-layer principle:** the entire core (job queue, database, pull-work-push sync, API integrations) lives in pure Go packages, with no dependency on Wails. Wails is only the shell (window, bindings, events). This makes it cheap to fall back to v2 or move up to stable if needed.
  - **Antivirus mitigation (false positive from Defender with Go binaries):** local builds (no Mark of the Web), no UPX/packers, always recent Go, and a Defender exclusion for the app folder on the user's machines. Code signing ruled out due to cost — acceptable because the app isn't distributed to third parties.
- **Frontend:** Svelte **5** (runes). TypeScript bindings generated by Wails v3 (officially supported Svelte template).
  - **Rationale for the switch (was React):** with AI agents, the bottleneck is definition and review, not code production — and the dev reviews with far more authority in Svelte 5 (direct prior experience, including runes) than in React, where the typical defects of generated code (unnecessary effects, wrong dependencies, duplicated state) would pass a superficial review.
  - **Known risk:** models still mix Svelte 4 patterns with Svelte 5. Mitigation: explicit conventions in `CLAUDE.md` (Svelte 5, runes, never legacy store syntax) + the dev's own experience as a reviewer.
  - The **validated React prototype** remains as the reference for UX and visual identity (dark theme; Sora fonts for display, Inter for body, JetBrains Mono for timestamps/data) — to be ported, not redesigned.

## Go stack

- **SQLite driver:** `modernc.org/sqlite` (pure-Go SQLite, no cgo).
  - Reason: avoids needing a C toolchain (MinGW) on Windows machines, standardizing the build (plain `go build` on every machine; the cgo that Wails requires on Linux doesn't change this). Lower performance than `mattn/go-sqlite3` (~2x on INSERTs) is irrelevant at the app's volume (dozens of lessons).
  - Confidence: it's SQLite's official C code mechanically transpiled (passes SQLite's own test suite); validated in production by projects like Litestream and Gogs.
  - **Cheap exit ramp:** file format identical to SQLite C and the `database/sql` interface — switching drivers (mattn or `ncruces/go-sqlite3`) means changing the import and the name in `sql.Open`, without touching the data. **Required discipline:** keep the SQL in the repository layer portable, with no driver-specific features.
  - **Snapshot for push:** `VACUUM INTO` (plain SQL, works with any driver) generates a consistent copy of the database while the app is open. Never copy the database file directly with open connections.
  - **Acceptable alternative:** `mattn/go-sqlite3` (cgo, exposes SQLite's Backup API), in case modernc runs into a blocking issue.
  - Database in **WAL mode** during use.
- **Migrations:** `pressly/goose`, with SQL files embedded in the binary via `embed.FS`.
  - **Pull compatibility rule:** when importing a database from another machine, compare the schema version; migrate if the database is older than the app, **refuse** (with a clear message) if the database is newer — a real scenario with machines updated at different times.
- **Job queue:** a `jobs` table in the same SQLite database + a **single worker** (goroutine) processing sequentially. No external job-queue crate/lib.
  - Columns: `id`, `lesson_id`, `kind` (`extract_audio` | `transcribe` | `analyze`), `status` (`pending` | `running` | `done` | `error`), `attempts`, `last_error`, `payload` JSON, timestamps.
  - Each pipeline step is its own job → enables selective reprocessing (re-analysis = a new `analyze` job over the existing transcript).
  - Idempotency: a job checks whether the output artifact already exists before running. Retry with an `attempts` count and simple backoff. On app startup, jobs stuck in `running` (crash) revert to `pending`.
  - The **prompt version** used in `analyze` jobs is its own column / FK to the versioned prompts table — it does not go in the `payload`.
- **HTTP (STT and LLM APIs):** stdlib `net/http`.
- **ffmpeg:** invoked via `os/exec`.
- **Credentials:** `zalando/go-keyring` — native OS secure storage (never in plain text).
- **`golang.org/x/sys`:** used only for `unix.Renameat2` (`services/move_noreplace_linux.go`) for the atomic *non-replacing* rename of the video when confirming the import (Story 3, standardized renaming) — it was already an indirect dependency via other libs, promoted to a direct one in this slice.
- **Sync manifest hash:** stdlib `crypto/sha256`.
- **Logs:** stdlib `log/slog`, to file (essential for debugging the background pipeline).

## Persistence

- **Database:** SQLite (single file, which enables the pull-work-push model and file-copy backups).
- **Credentials:** native OS secure storage (see Go Stack), never in plain text.

## File storage and sync

- **Cloud service:** Google Drive, via the Google Drive Desktop client (local synced folder). No use of the Google Drive API.

## Media processing

- **Audio extraction:** ffmpeg.

## Speech-to-text (transcription)

- **Requirements:** native diarization (student × tutor) and word-level timestamps.
- **Decision:** ElevenLabs Scribe (`scribe_v2`), with diarization (`diarize=true`, `num_speakers=2`)
  and native multilingual detection (no explicit `language_code` sent, to cover
  PT/ES code-switching). Reason: best diarization among the 4 candidates tested (Gladia,
  AssemblyAI, Deepgram, ElevenLabs) — a fatal criterion for the product, since corrections depend
  on knowing who spoke.
- **Documented alternative (not discarded):** AssemblyAI (Universal-2) — second-best
  diarization, more precise punctuation. Kept as a candidate for an alternative/selectable provider
  in the final app; the `stt.Provider` interface is already designed for multiple implementations, so
  adding STT provider selection to the Settings screen (the same pattern already planned for the
  LLM) is a cheap extension when/if it's prioritized.
- **Discarded:** Deepgram (poor diarization — the main issue observed) and Gladia (confuses
  speakers in overlapping-speech segments). Plain Whisper was also discarded (no native
  diarization — would require combining it with pyannote, unnecessary complexity).
- **Limitation of this decision:** made based on 1 lesson (lesson 01) from the sample — a conscious
  decision not to follow through with the full 3–5 lesson comparison originally planned in
  `fase-0-validacao.md` (Story 2), since the diarization difference between the candidates was
  already clear. If a quality problem shows up in production, revisit with more evidence.
- **Real measured cost** (~29–30 min lesson): ElevenLabs ~US$0.195 (~1.95k credits; 10k
  free credits/month). AssemblyAI ~US$0.112 (model + diarization; a one-time, non-recurring
  US$50 in free credits).

## LLM-based analysis

- **Decision:** DeepSeek (`deepseek-v4-flash`, cheapest tier), via an OpenAI-compatible
  endpoint (`/beta`, Chat Prefix Completion to force JSON output). Reason: quality sufficient for
  the application already on the first candidate tested (corrections, vocabulary — including PT/ES
  code-switching candidates — and tutor expressions, all useful in lesson 01), at negligible cost.
- **`deepseek-v4-pro` kept as a documented backup** (tested once on lesson 01, not the
  default provider): produced a **more in-depth** analysis than Flash's, but with **several
  inaccurate points**. Main hypothesis: the prompt (v1, unoptimized) is the cause of the
  inaccuracies, not a model limitation. Since Flash already found the desired highlights — what
  needed validating was the ability to process the transcript through a language-analysis lens, and
  the observed difference there was one of depth, not of essential coverage — Pro is kept in
  reserve (at ~3.6x the cost of Flash) as a candidate for a future "more in-depth analysis"
  option, after prompt refinement — see `docs/notas-analise-llm.md`.
- **Candidates kept on hold** (not eliminated, just untested): Qwen, GLM, Anthropic
  (Claude), OpenAI (GPT), Gemini. The `analysis.Provider` interface already abstracts the provider — switching or
  adding one means extending `openai_compatible.go` (or a dedicated client, if the API isn't
  compatible) with no structural change to the rest of the package. The final app's Settings
  screen still plans for provider/model selection.
- **Future exploration (not a decision, just a recorded intention):** evaluate even
  simpler/cheaper "flash" models for complementary analysis tasks (not the main analysis); and a
  possible more in-depth analysis option using `deepseek-v4-pro` (or similar) as a
  selectable alternative model, after refining the prompt.
- **Real measured cost** (~29–30 min lesson, lesson 01, 1 run): 8,575 prompt tokens + 725
  completion tokens = 9,300 total tokens → ~US$0.0014 (less than one US cent), at
  `deepseek-v4-flash` pricing (~US$0.14/M input, ~US$0.28/M output — `api-docs.deepseek.com/quick_start/pricing/`, July/2026).
- **Limitation of this decision:** made based on 1 run on 1 lesson (lesson 01), without running the
  optional comparison with Anthropic/OpenAI planned in `fase-0-validacao.md` (Story 3) — the same
  stance already adopted for the STT decision: enough evidence to close for now, revisit if a
  quality problem shows up in production.
